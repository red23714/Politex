# 3. Ход работы

## 3.1 Краткое описание класса MyString (формат хранения строки)

Класс `MyString` хранит символьную строку в виде «сырого» динамического
массива `char* pstr_`, выделяемого оператором `new[]` и освобождаемого
оператором `delete[]` (в деструкторе и при любом изменении внутреннего
буфера — через приватный метод `delete_pstr_change_params`). Контейнеры и
алгоритмы STL для самого хранения не используются; `std::string_view`
применяется только как унифицированный тип параметра, позволяющий
принимать на вход `const char*`, `std::string` и `MyString` без
дублирования кода (неявное приведение `MyString` к `std::string_view`
реализовано через `operator std::string_view() const`).

Класс хранит три поля:

- `pstr_` — указатель на буфer символов, всегда завершённый нулевым
  символом `'\0'`;
- `len_` — длина строки без учёта завершающего нуля (аналог `size()`
  у `std::string`);
- `capacity_` — размер выделенной памяти, включая место под `'\0'`
  (`capacity_ = len_ + 1` в «уплотнённом» состоянии).

Ёмкость увеличивается по мере необходимости при вставке (`my_insert`) и
уменьшается только в методе `shrink_to_fit`, что соответствует
требованию задания. Копирование объекта — глубокое (выделяется новый
буфер и в него копируются данные), перемещение — реализовано через
move-конструктор/move-присваивание с «обнулением» полей у исходного
объекта, что исключает двойное освобождение памяти.

Все операции, работающие с индексами и диапазонами
(`insert/erase/replace/substr/find/operator[]` и т. д.), проходят через
единый приватный метод `check_index`, который поддерживает Python-подобную
адресацию отрицательными индексами (индекс от конца строки) и
генерирует исключение `std::out_of_range` при выходе за границы —
это отвечает требованию задания об использовании исключений стандартной
библиотеки C++ для сигнализации об ошибочных аргументах.

## 3.2 Алгоритмическая декомпозиция класса (граф зависимостей методов)

Перед реализацией всех методов был проведён анализ, какие функции
являются «базовыми» (не выражаются через другие методы класса), а какие
можно реализовать поверх них. Это соответствует фактической структуре
кода:

**Базовые (примитивные) операции**

| Метод | Роль |
|---|---|
| `init(string_view)` | выделяет буфер под источник и копирует данные |
| `create_copy_of_pstr(int)` | создаёт копию текущего буфера нужного размера |
| `delete_pstr_change_params(...)` | освобождает старый буфер и подставляет новый |
| `my_insert(index, count, data)` | единственная точка, где реально происходит вставка данных в буфер |
| `check_index(...)` | валидация индекса/количества, поддержка отрицательных индексов |

**Производные операции (построены поверх базовых)**

```
my_insert ──┬─▶ insert(index, count, char)
            ├─▶ insert(index, source_str)
            ├─▶ insert(index, source_str, count)
            └─▶ insert(index, source_str, s_index, count)

insert ──▶ append(...)                       (append = insert в конец, index = len_)

erase ──▶ replace(...)   (replace = erase + insert)
erase ──▶ substr(...)    (substr = копия объекта + erase лишних частей + shrink_to_fit)

append/insert ──▶ operator+=  ──▶ operator+   (operator+ = копия + operator+=)

compare ──▶ operator==, !=, <, >, <=, >=

to_float ──▶ to_int

init ──▶ конструкторы от string_view/const char*/std::string/MyString (копирование)
insert ──▶ конструкторы MyString(int32_t), MyString(float)  (число «собирается» посимвольной вставкой)
```

Таким образом на первом занятии были реализованы базовые методы
(`init`, `create_copy_of_pstr`, `delete_pstr_change_params`, `my_insert`,
`check_index`) и минимальный набор конструкторов/геттеров, а на втором —
все производные методы, выражающиеся через них.

## 3.3 Результаты тестирования базовых методов

Базовые методы протестированы юнит-тестами из `test.py`

- `size()/capacity()/empty()` до и после `append`;
- `clear()` — обнуляет `len_` и, что важно, **не изменяет** `capacity_`

  соответствует требованию «ёмкость уменьшается только в
  `shrink_to_fit`»;
- `shrink_to_fit()` — после `append` + `erase` ёмкость больше длины,
  после `shrink_to_fit()` ёмкость становится равна `size() + 1`.

Все перечисленные тесты успешно проходят на текущей реализации — логика
`init`, `create_copy_of_pstr`, `delete_pstr_change_params` работает
корректно для «нормальных» (валидных) входных данных.

## 3.5 Реализация Python-обёртки

Обёртка `my_string_wrapper.cpp` реализована с помощью **Boost.Python** и
регистрирует класс `MyString` как тип `my_string.MyString`.

Ключевые решения:

1. **Универсальный конвертер `string_view_from_python`.** Поскольку все
   методы класса принимают `std::string_view` (что и обеспечивает
   поддержку трёх типов `SOURCE_STR`), в обёртке зарегистрирован
   `rvalue`-конвертер, который умеет строить `std::string_view` из:
   - Python `str` (через `PyUnicode_AsUTF8AndSize`);
   - Python `bytes` (через `PyBytes_AsStringAndSize`);
   - объекта `MyString` (берётся его `c_str()`/`size()` напрямую, без
     копирования).

   Это позволяет вызывать, например, `s.insert(2, "ABC")`,
   `s.insert(2, b"ABC")` и `s.insert(2, other_my_string)` одной и той же
   C++ перегрузкой.

2. **Разрешение неоднозначности перегрузок.** Так как в C++ у `insert`,
   `append`, `replace`, `find`, `substr` по нескольку перегрузок с разным
   числом параметров, для Boost.Python каждая перегрузка явно приведена
   к нужному типу указателя на метод через `static_cast<...>(&MyString::...)`
   — иначе компилятор не смог бы выбрать, какую именно перегрузку
   экспортировать под одним и тем же именем.

3. **Отдельные свободные функции-«прослойки»** для операций, которые
   неудобно/нельзя экспортировать напрямую:
   - `assign_string` / `assign_char` / `assign_my_string` — три отдельные
     Python-функции `assign`/`assign_char`, так как в C++
     `operator=(std::string_view)` и `operator=(char)` нельзя
     напрямую замэппить на один и тот же Python-метод с перегрузкой по
     типу без дополнительной обвязки, а присваивание в Python обычно
     не делают через `operator=`, а через явный метод;
   - `getitem`/`setitem` — реализация `__getitem__`/`__setitem__` поверх
     `operator[]`;
   - `to_py_str` — реализация `__str__`/`__repr__`, конвертирующая
     `MyString` в `std::string` для Python.

4. **Поддержка стандартных Python-протоколов**: арифметика (`__add__`,
   `__iadd__`), сравнение (`__eq__`, `__ne__`, `__lt__`, `__gt__`,
   `__le__`, `__ge__`), длина (`__len__`), строковое представление
   (`__str__`, `__repr__`), индексация (`__getitem__`/`__setitem__`) —
   это делает объект `MyString` в Python внешне неотличимым от
   обычной изменяемой строки.

# Обнаруженные ошибки

При подготовке отчёта код был скомпилирован и протестирован (g++ 13,
`-std=c++17`, с санитайзерами `AddressSanitizer`/`UndefinedBehaviorSanitizer`,
а также со специальным флагом `-ftrivial-auto-var-init=pattern`,
заполняющим неинициализированную память детерминированным «мусором» —
это нужно, чтобы гарантированно воспроизвести ошибки, которые иначе
проявляются не всегда, в зависимости от содержимого стека). Ниже —
перечень найденных проблем с конкретными аргументами, при которых они
проявляются. Соответствующие тесты добавлены в `test.py`
(класс `TestMyStringKnownIssues`, помечены `@unittest.expectedFailure`) —
после исправления кода уберите этот декоратор, и тест должен начать
проходить.

1. **Проект не компилируется «как есть» (g++ 13 / libstdc++, `-std=c++17`).**
   В `MyString::operator=(std::string_view source_str)` строка
   `if (*this != source_str)` неоднозначна: одновременно подходят
   `MyString::operator!=(const MyString&)` (через неявное преобразование
   `string_view → MyString`) и свободный `std::operator!=(string_view, string_view)`
   (через неявное преобразование `MyString → string_view`). Компилятор
   выдаёт `error: ambiguous overload for 'operator!='`.
   **Исправление:** явно привести к одному типу, например
   `if (std::string_view(*this) != source_str)`.

2. **`operator>>(std::ifstream&, MyString&)` — пустая заглушка.**
   Тело функции пустое и не содержит `return`, хотя тип возврата —
   ссылка. Компилятор предупреждает
   `warning: no return statement in function returning non-void`;
   любой вызов оператора — неопределённое поведение (по сути, функция
   не реализована, хотя заявлена в доп. задании 6.1, п. 5-6).

3. **Конструкторы `MyString(int32_t)` и `MyString(float)` используют
   неинициализированные поля.** В отличие от остальных конструкторов,
   они не вызывают `init()` и не задают `pstr_/len_/capacity_` явно —
   расчёт идёт на то, что `my_insert` сам создаст буфер при
   `capacity_ == 0`. Но `len_` и `capacity_` не имеют инициализатора по
   умолчанию в классе, поэтому на практике содержат «мусор» из памяти,
   а не гарантированный 0. Подтверждено экспериментально: при
   детерминированном заполнении памяти ненулевым паттерном вызов
   `MyString(0)` (как и любое другое число) приводит к необработанному
   исключению `std::out_of_range` и аварийному завершению программы.
   Аргументы для воспроизведения: `MyString(0)`, `MyString(12345)`,
   `MyString(-42)`, `MyString(3.14f)` — падает (или даёт мусорный
   результат) при "невезучем" содержимом стека.
   **Исправление:** в начале обоих конструкторов явно инициализировать
   `pstr_ = nullptr; len_ = 0; capacity_ = 0;` (или вызвать общий
   `init(std::string_view())`) перед первым `insert`.

4. **`compare()` не является лексикографическим сравнением**, хотя
   этого явно требует задание. Функция сначала сравнивает *длины*
   строк и только при равенстве длин — посимвольно. Это даёт неверный
   результат всякий раз, когда более короткая строка лексикографически
   больше более длинной.
   Пример: `compare("z", "aa")` возвращает `-1` (то есть "z" < "aa"),
   хотя при посимвольном сравнении, как это делает `std::string`,
   `'z' > 'a'`, и правильный результат — `"z" > "aa"` (`> 0`). Ошибка
   влияет также на все операторы сравнения `<, >, <=, >=`, построенные
   на `compare()`, — они дадут неверный порядок при сортировке строк
   разной длины.
   **Исправление:** сравнивать посимвольно до `min(len_, other.len_)`,
   и только если все совпавшие символы равны — использовать разницу
   длин как решающий критерий (аналогично `std::string::compare`).

5. **`find()` с пустой искомой строкой возвращает `-1`.**
   Аргумент: `s.find("")`. Ожидаемое (по аналогии с `std::string::find`,
   на которую явно ссылается методичка) поведение — вернуть индекс,
   с которого начат поиск (обычно 0), а не «не найдено».
   **Исправление:** в `find` для `m == 0` возвращать `index`, а не `-1`.

6. **`at(index)` не проверяет наличие буфера и падает вместо выброса
   исключения.** Для строки, полученной конструктором по умолчанию
   (`MyString s;`, `pstr_ == nullptr`, `capacity_ == 0`), вызов
   `s.at(0)` проходит проверку `check_index` (так как `index (0) <=
   capacity_ (тут используется len_=0)`) и затем разыменовывает
   `pstr_[0]`, то есть `nullptr[0]` — подтверждённый `SIGSEGV`
   (AddressSanitizer: `SEGV on unknown address 0x0...`, "load of null
   pointer").
   **Исправление:** в `at()`/`check_index` дополнительно проверять
   `index < len_` (а не `<= capacity`), чтобы `at()` на пустой строке
   всегда бросал `std::out_of_range`, как того требует описание метода
   в задании ("иначе генерирует исключение").

7. **`to_float()`/`to_int()` падают на пустой строке по той же причине**
   — обращение к `pstr_[0]` без проверки `len_ == 0`. Аргумент:
   `MyString().to_float()` (или `to_int()`). Подтверждено ASan:
   `SEGV ... load of null pointer ... in MyString::to_float()`.
   **Исправление:** в начале `to_float()` добавить проверку
   `if (len_ == 0) return 0.0f;` (аналогично для `to_int()`, если он не
   переиспользует `to_float()` — сейчас переиспользует, так что
   достаточно одной проверки).

8. **`MyString(int count, char ch)` не проверяет `count >= 0`.**
   Аргумент: `MyString(-1, 'x')`. Отрицательное `count` даёт
   `capacity_ = count + 1 = 0`, а `len_ = count = -1`; при неявном
   приведении к `size_t` в `new char[capacity_]`/`std::memset(pstr_, ch,
   count)` происходит попытка операции с "огромным"/отрицательным
   размером. Подтверждено ASan: `negative-size-param: (size=-1)` в
   `std::memset` внутри конструктора — крах программы.
   **Исправление:** в начале конструктора бросать `std::out_of_range`
   (или аналогичное исключение) при `count < 0`, как это уже сделано,
   например, в `insert(index, count, ch)`.

9. **Присваивание строки, "перекрывающейся" с собственным буфером
   объекта, приводит к use-after-free.** `operator=(std::string_view)`
   сначала освобождает старый буфер (`delete_pstr_change_params(nullptr,
   0, 0)`, внутри — `delete[] pstr_`), а затем в `init()` читает данные
   из `source_str` — но если `source_str` указывал куда-то внутрь
   *того же* (уже удалённого) буфера, чтение идёт из освобождённой
   памяти. Пример на чистом C++:
   `std::string_view v(s.c_str() + 7, 5); s = v;` — где `v` указывает
   внутрь буфера самого `s`. Подтверждено ASan:
   `heap-use-after-free ... READ of size 5 ... freed by
   delete_pstr_change_params ... previously allocated by MyString::init`.
   Через штатный Python-интерфейс эта ошибка недостижима (Python-обёртка
   всегда передаёт либо независимую копию `std::string`, либо явно
   защищённое самоприсваивание `MyString`), поэтому тест на неё в
   `test.py` не добавлен — она актуальна только для прямого
   использования класса на C++ (например, будущими доп. заданиями с
   итераторами/DLL).
   **Исправление:** либо скопировать данные `source_str` во временный
   буфер до удаления старого, либо (эффективнее) проверять, лежит ли
   `source_str.data()` в диапазоне `[pstr_, pstr_ + capacity_)`, и в
   этом случае обрабатывать как самоприсваивание своей же подстроки.

**Дополнительно, без падений, но стоит проверить перед защитой:**

- В `clear()` вызывается `std::memset(pstr_, 0, capacity_)`. Для
  объекта, созданного конструктором по умолчанию (`pstr_ == nullptr`,
  `capacity_ == 0`), это вызов `memset(nullptr, 0, 0)` — формально
  неопределённое поведение по стандарту C (передача null-указателя в
  `memset` запрещена даже при размере 0), хотя на всех распространённых
  реализациях это безвредно. Рекомендуется добавить `if (pstr_)` перед
  вызовом либо привести объект после конструктора по умолчанию к
  состоянию "как после `init(\"\")`" (`capacity_ = 1`, `pstr_` указывает
  на `"\0"`), что заодно упростит и исправление ошибок №3, 6, 7 выше.
- Обёртка не регистрирует Boost.Python `exception translator` для
  `std::out_of_range`/`std::invalid_argument`. У современных версий
  Boost.Python есть базовая трансляция стандартных исключений в
  `RuntimeError`, но это стоит явно проверить сборкой и тестом вида
  `self.assertRaises(...)` на реальном модуле — если трансляции нет,
  исключение из C++ приведёт не к Python-исключению, а к аварийному
  завершению интерпретатора.
